### 🏁 The Mission
Lab 10's triage heap builds itself up one patient at a time, each `insert` costing $O(\log n)$ — fine for patients arriving one by one, but USI's annual hackathon judging system has a different problem: it already has all 5,000 submission scores sitting in a plain list at once, and it needs the heap built from all of them *before* judging starts, as fast as possible. Building it via 5,000 individual inserts would waste time re-proving what the data structure already knows about itself. Your task is to implement the classic **O(n) bottom-up heapify**, then use it to power a "Top-K" leaderboard query without ever fully sorting the submissions.

### Part A: Why Heapify Beats Repeated Insertion (50 Points)
**Instructions:** Answer the following questions in a separate document (PDF or Markdown). Show all work.

1. **The Naive Cost:**
   State the total time complexity of building a heap of `n` elements by calling `insert` (Lab 10's $O(\log n)$ operation) `n` times in a row. Show the summation that gets you there.
2. **The Heapify Insight:**
   Bottom-up heapify instead calls `_sift_down` (not `_sift_up`) on every non-leaf node, starting from the *last* non-leaf node and working back to the root. Explain in one or two sentences why starting from the bottom and working up guarantees that, by the time `_sift_down` is called on a given node, both of its subtrees are already valid heaps.
3. **The O(n) Proof:**
   The classic result is that bottom-up heapify runs in $O(n)$ total, not $O(n \log n)$, even though it calls `_sift_down` (an $O(\log n)$ operation) on roughly `n/2` nodes. The intuition: most nodes are near the bottom of the tree, where `_sift_down` has very little distance left to travel.
   - Using the fact that there are roughly `n / 2^(h+1)` nodes at height `h` in a complete binary tree, and each such node's `_sift_down` costs $O(h)$, set up (but you do not need to fully evaluate) the summation $\sum_{h=0}^{\log n} \frac{n}{2^{h+1}} \cdot h$ that bounds the total work. State, without deriving the closed form, why this sum converges to $O(n)$ rather than growing with $\log n$.
4. **Base Case Reasoning (Brutality Clause applies):**
   Your `_sift_down` from Lab 10 is recursive. State its base case precisely as it applies inside `heapify`'s loop (a node with no children, or whose children are already smaller), and explain why heapify's bottom-up node order guarantees every call to `_sift_down` reaches that base case rather than recursing forever.

   > [!CAUTION]
   > **The Brutality Clause:** Any recursive reasoning missing an explicitly stated base case receives an automatic **0** on that portion of the question.

### Part B: The Heap Builder (50 Points)

**Requirements:**
1. `heapify(data: List[float]) -> None` must convert `data` **in place** into a valid min-heap using the bottom-up approach from Part A — starting from the last non-leaf index and calling `_sift_down` backward to the root. 2. `find_k_largest(data: List[float], k: int) -> List[float]` must return the `k` largest values from `data`, **without fully sorting** `data`. 3. `find_k_largest` must run in $O(n \log k)$, not $O(n \log n)$ — never build a heap of all `n` elements to answer this query.
